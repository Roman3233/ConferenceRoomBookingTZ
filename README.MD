# Conference Room Booking API

REST API для управління конференц-залами, бронюванням та розрахунком вартості оренди. Тестове завдання на позицію Trainee/Junior .NET Engineer.

## Бізнес-завдання

Компанія здає в оренду конференц-зали для бізнесу. API дозволяє:

- керувати конференц-залами (створення, редагування, видалення);
- шукати доступні зали за датою, часом і місткістю;
- бронювати зал з обраними додатковими послугами;
- автоматично розраховувати вартість оренди залежно від часу доби;
- переглядати звіти про дохід і завантаженість залів.

## Технічний стек

- **.NET 9**, ASP.NET Core Web API
- **Swashbuckle.AspNetCore** — документація API (Swagger UI)
- **xUnit** — юніт-тести
- Сховище даних: **in-memory** (`List<T>` за інтерфейсами репозиторіїв)

### Чому in-memory

Фокус завдання — бізнес-логіка , а не робота з БД. Усі репозиторії приховані за інтерфейсами, тому заміна на EF Core в майбутньому не вимагає змін у бізнес-логіці — лише нову реалізацію інтерфейсів і зміну lifetime у DI.

## Архітектура проєкту

Проєкт розділений на 4 бібліотеки:

```
ConferenceRoomBooking/
├── ConferenceRoomBooking.Api/            # Контролери, DTO, Program.cs, Swagger
│   ├── Controllers/
│   ├── DTOs/
│   └── Middleware/         # Глобальна обробка помилок
├── ConferenceRoomBooking.Core/           # Домен: моделі, інтерфейси, бізнес-логіка
│   ├── Models/
│   ├── Interfaces/
│   └── Services/
├── ConferenceRoomBooking.Infrastructure/ # Реалізація сховища (in-memory)
│   └── Repositories/
└── ConferenceRoomBooking.Tests/          # Юніт-тести (xUnit)
```

### Шари й відповідальність

|Шар|Відповідальність|
|---|---|
|**Controllers**|Приймають HTTP-запит, валідують DTO, делегують сервісам, повертають HTTP-відповідь. Не містять бізнес-логіки.|
|**Services (Core)**|Бізнес-правила: валідація, перевірка доступності, розрахунок вартості, координація репозиторіїв.|
|**Repositories (Infrastructure)**|Зберігання й читання даних. Реалізують інтерфейси з `Core`, тому деталі зберігання приховані від решти системи.|
|**Models (Core)**|Доменні сутності — не залежать від жодного іншого шару.|
### Ключові сутності

- **Room** — конференц-зал: назва, місткість, базова ціна за годину, список доступних послуг.
- **Service** — послуга із загального каталогу (Проєктор, Wi-Fi, Звук тощо): назва, ціна.
- **Booking** — бронювання: зал, дата, час, обрані послуги. Зберігає snapshot цін на момент бронювання (`RoomCostAtBooking`, `BookedService.PriceAtBooking`), щоб майбутня зміна цін не впливала на вже підтверджені бронювання.
## Розрахунок вартості оренди

Вартість оренди залежить від часу доби:

|Період|Множник|
|---|---|
|06:00–09:00 (ранкові)|×0.9 (знижка 10%)|
|09:00–12:00 (стандартні)|×1.0|
|12:00–14:00 (пікові)|×1.15 (націнка 15%)|
|14:00–18:00 (стандартні)|×1.0|
|18:00–23:00 (вечірні)|×0.8 (знижка 20%)|


При старті застосунок автоматично заповнюється початковими даними (`DataSeeder`):

**Зали:**

- Зал B — 100 осіб, 3500 грн/год
- Зал C — 30 осіб, 1500 грн/год

**Послуги (доступні для всіх трьох залів):**

- Проєктор — 500 грн
- Wi-Fi — 300 грн
- Звук — 700 грн

## API Ендпоінти

### Зали (`/api/rooms`)

|Метод|Ендпоінт|Опис|
|---|---|---|
|`POST`|`/api/rooms`|Створити зал|
|`GET`|`/api/rooms`|Список усіх залів|
|`GET`|`/api/rooms/{id}`|Зал за ID|
|`PUT`|`/api/rooms/{id}`|Оновити зал (часткове оновлення — передаються лише поля, що змінюються)|
|`DELETE`|`/api/rooms/{id}`|Видалити зал|
|`GET`|`/api/rooms/available`|Пошук доступних залів за датою, часом і мінімальною місткістю|

### Бронювання (`/api/bookings`)

|Метод|Ендпоінт|Опис|
|---|---|---|
|`POST`|`/api/bookings`|Забронювати зал з розрахунком вартості|
|`GET`|`/api/bookings`|Список усіх бронювань|
|`GET`|`/api/bookings/{id}`|Бронювання за ID|

### Послуги (`/api/services`)

|Метод|Ендпоінт|Опис|
|---|---|---|
|`POST`|`/api/services`|Додати послугу до загального каталогу|
|`GET`|`/api/services`|Список усіх послуг|
|`GET`|`/api/services/{id}`|Послуга за ID|
|`DELETE`|`/api/services/{id}`|Видалити послугу|

> **Важливо:** створення послуги додає її лише до загального каталогу — вона не стає автоматично доступною в жодному залі. Щоб послугу можна було обрати при бронюванні конкретного залу, її потрібно додати до списку `serviceIds` цього залу через `PUT /api/rooms/{id}`. 
### Обробка помилок

Усі необроблені винятки перехоплюються глобальним middleware (`ExceptionHandlingMiddleware`) і перетворюються на структуровану відповідь `{ "error": "..." }` з відповідним HTTP-кодом:

- `400 Bad Request` — некоректні вхідні дані (валідація DTO або `ArgumentException`)
- `404 Not Found` — сутність не знайдена
- `409 Conflict` — запит суперечить поточному стану системи (наприклад, зал уже заброньований на цей час)
- `500 Internal Server Error` — непередбачена помилка (клієнту повертається загальне повідомлення, без внутрішніх деталей — з міркувань безпеки)

## Звіти та аналітика

### `GET /api/reports/revenue?startDate=...&endDate=...`

Загальний дохід за період з розбивкою на дохід від оренди залів і дохід від додаткових послуг.

### `GET /api/reports/occupancy?startDate=...&endDate=...`

Завантаженість кожного залу за період: кількість заброньованих годин і відсоток завантаженості відносно робочого часу (06:00–23:00, 17 годин на добу).

## Тести

Проєкт `ConferenceRoomBooking.Tests` містить юніт-тести на найважливішу логіку:

- **`PricingCalculatorTests`** — розрахунок вартості для кожної часової зони окремо та для бронювань, що перетинають кілька зон; перевірка граничних випадків (некоректний інтервал, час поза робочими годинами).
- **`BookingServiceTests`** — створення бронювання з коректним розрахунком вартості, перевірка конфлікту при перетині часу бронювань.

Запуск тестів:

```bash
dotnet test
```

## Архітектурні рішення та відомі обмеження

- **Async/await відсутній.** Репозиторії — in-memory, без реального I/O (мережа, диск, БД), тому асинхронність не додає користі, лише зайву складність. При переході на EF Core інтерфейси репозиторіїв варто буде зробити асинхронними (`Task<T>`), а lifetime у DI змінити з `Singleton` на `Scoped` (кожен запит отримує власний `DbContext`).
